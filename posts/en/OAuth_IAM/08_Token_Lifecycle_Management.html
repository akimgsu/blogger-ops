08. Token Lifecycle Management

Issuing a token is only the beginning. Long-lived access tokens enlarge breach windows; overly short ones destroy UX. Refresh tokens and silent refresh resolve that tension.

Access Tokens: Short-Lived Working Keys

Access tokens call APIs. Keep TTLs short (minutes to about an hour), store them where JavaScript cannot freely read them when possible, and include only necessary claims.

Refresh Tokens: Longer-Lived Renewal Keys

POST /token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&
refresh_token=8xLOxBtZp8&
client_id=my-web-app&
client_secret=SECRET

Refresh tokens are more sensitive. Prefer rotation on use and reuse detection to spot theft.

Why Split the Two?

Frequently exposed credentials should be short-lived. Rarely used renewal secrets can live longer under stronger protection. That separation balances security and seamless sessions.

Silent Refresh Logic

Silent refresh renews tokens without showing a login UI—typically via the refresh-token grant through a BFF or secure cookie endpoint.

async refresh() {
  const res = await fetch("/auth/refresh", {
    method: "POST",
    credentials: "include"
  });
  if (!res.ok) throw new Error("REFRESH_FAILED");
  const data = await res.json();
  this.accessToken = data.access_token;
  return this.accessToken;
}

Combine proactive refresh (before expiry) with reactive retry on 401. Deduplicate concurrent refreshes with a single-flight promise.

let refreshPromise = null;
function refreshSingleFlight() {
  if (!refreshPromise) {
    refreshPromise = doRefresh().finally(() => { refreshPromise = null; });
  }
  return refreshPromise;
}

Chapter Summary

  • Access tokens are short-lived API credentials; refresh tokens renew them.
  • Silent refresh preserves UX while keeping access TTLs short.
  • Rotate refresh tokens and single-flight concurrent renewals.
  • Separate purpose and storage for each token type.
