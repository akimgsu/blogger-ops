06. Bearer Token and JWT

The most common API credential header is Authorization: Bearer <token>. This chapter explains what “bearer” means, how JWTs are built, and the critical warning that Base64 is not encryption.

What “Bearer” Means

Per RFC 6750, possession of the token is enough to exercise its privileges—like a movie ticket. Whoever holds a valid ticket gets in. That is why HTTPS, careful storage, and short lifetimes are mandatory.

JWT Anatomy

A JWT is three Base64URL parts separated by dots:

base64url(header).base64url(payload).base64url(signature)

Header

{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "2026-08-key"
}

Payload

{
  "iss": "https://auth.example.com/",
  "sub": "user-123",
  "aud": "https://api.example.com",
  "exp": 1760000000,
  "scope": "orders:read profile"
}

Signature

The signature prevents tampering. Resource servers verify with a public key and must pin allowed algorithms to avoid algorithm confusion attacks.

function verifyBearerJwt(token, publicKey) {
  return jwt.verify(token, publicKey, {
    algorithms: ["RS256"],
    issuer: "https://auth.example.com/",
    audience: "https://api.example.com"
  });
}

Base64 Encoding Is Not Encryption

Anyone can decode the header and payload. Signatures ensure integrity, not confidentiality. Do not put government IDs, password hashes, or sensitive PII in access-token payloads. Use JWE or keep secrets server-side.

echo 'eyJzdWIiOiIxMjM0Iiwicm9sZSI6ImFkbWluIn0' | base64 -d
# {"sub":"1234","role":"admin"}

Chapter Summary

  • Bearer tokens grant rights to whoever possesses them.
  • JWTs contain header, payload, and signature; verification is the trust root.
  • Base64URL is readable encoding, not encryption.
  • Validate alg/iss/aud/exp, use HTTPS, and keep TTLs short.
