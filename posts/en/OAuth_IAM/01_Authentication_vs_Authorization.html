01. Authentication vs Authorization

Two words dominate every security design conversation: Authentication and Authorization. Casual speech often blends them, but engineering must keep them strictly separate. Confusing the two leads to broken token design, over-privileged access, and serious incidents.

Authentication: “Who Are You?”

Authentication verifies that a principal is who they claim to be. Typical factors include something you know (password), something you have (OTP or hardware key), and something you are (biometrics).

After a successful login, systems usually issue a session or token so subsequent requests do not require re-entering credentials. That credential asserts identity—not permissions.

async function authenticate(username, password) {
  const user = await findUserByUsername(username);
  if (!user) throw new Error("USER_NOT_FOUND");

  const ok = await verifyPassword(password, user.passwordHash);
  if (!ok) throw new Error("INVALID_CREDENTIALS");

  // Authentication success → issue an identity credential
  return issueCredential({ sub: user.id, email: user.email });
}

Authorization: “What Are You Allowed to Do?”

Authorization decides whether an already authenticated principal may perform a specific action on a specific resource. Being logged in does not grant unlimited API access.

  • Role-based (RBAC): user, editor, admin
  • Scopes/permissions: orders:read, orders:write
  • Attributes/policies (ABAC): department, plan, resource ownership
function authorize(user, action, resource) {
  if (user.roles.includes("admin")) return true;
  if (action === "update" && resource.ownerId === user.id) return true;
  return false;
}

Real-World Analogy: ID Card vs Building Badge

A government ID proves identity (authentication). A building access badge decides which floors and rooms you may enter (authorization). The same person can have different badges as roles change.

Historically, HTTP uses 401 for authentication failure and 403 for authorization failure—names that still confuse newcomers.

Why Separation Matters for OAuth and IAM

Modern systems often split responsibilities: an IdP issues credentials, while APIs enforce scopes and roles. When the boundary collapses, teams fall into password sharing, “login equals full access,” and unauditable permission models.

OAuth 2.0 is fundamentally an authorization delegation framework. Standardized end-user authentication arrives with OpenID Connect. Understanding this distinction is the starting point of the entire series.

Chapter Summary

  • Authentication verifies identity; authorization checks permissions for that identity.
  • ID cards authenticate; building badges authorize.
  • By convention, use 401 for authn failures and 403 for authz failures.
  • Correct OAuth/IAM design begins by separating login from permission delegation.
