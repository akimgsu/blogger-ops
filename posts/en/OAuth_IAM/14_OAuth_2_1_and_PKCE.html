14. Modern Standards: OAuth 2.1 and PKCE

OAuth 2.0 succeeded, but some early grants aged poorly. OAuth 2.1 consolidates security best practices—especially retiring Implicit flow and centering Authorization Code + PKCE.

OAuth 2.1 Directions That Matter

  • Authorization Code + PKCE as the default for public clients
  • Implicit grant removed
  • Resource Owner Password Credentials grant removed/discouraged
  • No bearer tokens in query strings; exact redirect URI matching

Why Implicit Flow Was Deprecated

Implicit returned access tokens in URL fragments to SPAs that could not keep secrets. Fragments leak via history, logs, Referer, and extensions; there is no one-time code buffer; refresh handling is awkward. Modern browsers can do Auth Code + PKCE instead.

PKCE: Mathematical Defense Against Code Theft

  1. Client creates a high-entropy code_verifier
  2. Computes code_challenge = BASE64URL(SHA256(code_verifier)) (S256)
  3. Sends only the challenge to /authorize
  4. Later sends the verifier to /token
  5. Server accepts the exchange only if the hash matches
async function createPkcePair() {
  const verifier = base64UrlEncode(crypto.randomBytes(32));
  const challenge = base64UrlEncode(
    crypto.createHash("sha256").update(verifier).digest()
  );
  return { verifier, challenge };
}

Stealing the authorization code without the verifier fails at token exchange—critical for mobile and other redirect-interception scenarios.

Adoption Checklist

  • Remove Implicit and Password grants
  • Require PKCE S256 for public clients
  • Optionally add PKCE even for confidential clients
  • Keep state—PKCE does not replace CSRF protection

Chapter Summary

  • OAuth 2.1 hardens defaults around Auth Code + PKCE.
  • Implicit exposed tokens on the front channel and is obsolete.
  • PKCE binds code exchange to a secret verifier via SHA-256.
  • Use PKCE and state together.
