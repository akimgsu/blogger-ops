12. Cloud-Managed IdP: AWS Cognito Integration

If operating your own IdP is too costly, Amazon Cognito is the common AWS-managed option. The key is distinguishing User Pools from Identity Pools.

User Pool vs Identity Pool

User Pool = Authentication (IdP)

Handles sign-up/sign-in, MFA, app clients, and optional social/SAML/OIDC federation. Outputs ID, access, and refresh tokens.

Identity Pool = Temporary AWS Credentials

Exchanges an authenticated identity for short-lived AWS keys so clients can call S3, DynamoDB, and other AWS APIs under IAM roles.

[User] -> User Pool -> JWTs -> API Gateway / backend
                         \-> Identity Pool -> AWS creds -> S3

If the browser never talks to AWS APIs directly, a User Pool alone is often enough.

User Pool Design Checklist

  • Public vs confidential app clients
  • Exact callback and logout URLs
  • Hosted UI versus custom UI + SDK
  • Required attributes and token TTLs
  • Groups / Pre Token Generation for custom claims
const verifier = CognitoJwtVerifier.create({
  userPoolId: process.env.COGNITO_USER_POOL_ID,
  tokenUse: "access",
  clientId: process.env.COGNITO_CLIENT_ID
});

Identity Pool Roles

Use authenticated roles for signed-in users and keep unauthenticated roles disabled or extremely limited. Prefix S3 paths with Cognito identity IDs to enforce per-user home directories.

Social Federation Architecture

Wire Google/Apple into the User Pool so your app validates Cognito tokens only—no per-provider verification forks.

Chapter Summary

  • User Pools authenticate users; Identity Pools mint AWS credentials.
  • Most API backends primarily verify User Pool JWTs.
  • Social IdPs federate into Cognito for a single token format.
  • Client type, callbacks, TTLs, and role mapping drive secure designs.
