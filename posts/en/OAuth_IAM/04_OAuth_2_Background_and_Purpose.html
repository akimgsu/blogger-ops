04. OAuth 2.0 Background and Purpose

Before “Sign in with Google” felt normal, third-party apps often asked for your real passwords. That convenience was a security disaster. OAuth 2.0 exists to delegate limited access without sharing credentials.

The Password Anti-Pattern

Users typed their Google password into a printing app; the app logged in as the user and accessed mail or Drive freely. Consequences include credential sprawl, no least privilege, weak revocation, and missing consent UX.

OAuth’s goal is simple: delegate scoped access, and revoke it later—without sharing passwords.

What OAuth Solves—and What It Does Not

RFC 6749 defines an authorization framework. It explains how a client accesses protected resources on behalf of a resource owner. By itself, it is not a complete authentication protocol for proving “who is at the keyboard.” OpenID Connect later fills that gap.

The Four Core Roles

  1. Resource Owner: usually the end user who owns the data
  2. Client: the application requesting access (web, SPA, mobile, or server)
  3. Authorization Server: authenticates the user, collects consent, issues tokens
  4. Resource Server: hosts APIs and validates access tokens

In OAuth vocabulary, “client” means the application—not the browser.

Scopes: The Language of Least Privilege

GET /authorize?
  response_type=code&
  client_id=print-app&
  redirect_uri=https://print.example.com/callback&
  scope=drive.readonly&
  state=xyz

Users can approve read-only Drive access and later revoke the app—control that password sharing never offered.

function handleDriveList(req) {
  const claims = verify(extractBearer(req));
  if (!claims.scope.split(" ").includes("drive.readonly")) {
    return { status: 403, error: "insufficient_scope" };
  }
  return listFiles(claims.sub);
}

Chapter Summary

  • The password anti-pattern shares real credentials with third parties—OAuth replaces that with scoped delegation.
  • OAuth 2.0 authorizes access; it is not a standalone authentication protocol.
  • Master the four roles and scopes to reason about any OAuth deployment.
  • Consent and revocation restore user control.
