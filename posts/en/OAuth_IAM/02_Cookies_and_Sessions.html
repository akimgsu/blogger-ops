02. Cookies and Sessions

HTTP was designed as a stateless protocol. Servers forget prior requests unless the application adds state. Shopping carts, login state, and multi-step forms forced the industry toward the classic pair: cookies and sessions.

What Is a Cookie?

A cookie is a small piece of data the server asks the browser to store and resend on later requests via Set-Cookie / Cookie headers.

HTTP/1.1 200 OK
Set-Cookie: session_id=abc123; Path=/; HttpOnly; Secure; SameSite=Lax
  • HttpOnly: not readable by JavaScript (harder XSS theft)
  • Secure: sent only over HTTPS
  • SameSite: mitigates CSRF

What Is a Session?

In practice, “login session” usually means: the server stores session data (userId, roles, cart), while the browser holds only a session ID cookie. Each request looks up that ID in server memory, a database, or Redis.

app.post("/login", async (req, res) => {
  const user = await validateCredentials(req.body);
  req.session.userId = user.id;
  req.session.roles = user.roles;
  res.json({ ok: true });
});

The real state lives on the server—hence stateful authentication.

Strengths of Stateful Sessions

  • Immediate logout by deleting server-side session data
  • Sensitive claims stay off the client
  • Straightforward in monolithic server-rendered apps

Limits of Server Memory Management

In-process sessions vanish on restart, break with multi-instance load balancing unless sticky sessions or a shared store are used, and grow expensive under load. Redis helps, but you still operate a central state store.

Why Sessions Hurt in the MSA Era

Microservices amplify friction: shared session schemas couple teams, cookie domain rules get messy across gateways, central stores become bottlenecks, and mobile or partner API clients prefer bearer tokens over browser cookies.

Sessions are not “wrong”—they become costly in distributed, multi-client systems. That cost pushed the industry toward token-based, more stateless designs and eventually OAuth 2.0.

Chapter Summary

  • Cookies carry small client data; sessions typically keep state on the server behind a session ID.
  • Sessions excel at immediate revocation and server-side control.
  • Shared stores, scaling, and cross-domain constraints become expensive at scale.
  • MSA and diverse clients motivate token-based approaches.
